新增的發布狀態徽章：

- `✅ 已上線` — 名片改動已包含在最近一次重建中
- `⏳ 待重建` — 改動晚於上次重建，約 1–2 分鐘生效
- `⏳ 待發布` — 自動重建未設定或手動模式，無法預測何時生效
- 狀態**會自動更新**：每 20 秒輪詢一次（分頁在背景時暫停），
  重建完成後徽章自己變成「已上線」，不需要重新整理

> 判定方式：拿名片的 `updated_at` 與「上次成功重建時間」相比。
> 重建是全站重建，所以「改動早於重建」就必定已包含在那一輪輸出裡。
> 這是可靠的近似 —— 後端 KV 並沒有記錄每張名片各自的發布狀態。

### ⚠️ 一個要留意的曝光點

`https://tobyyipwork.github.io/sage/ecard/admin/public/` 目前回傳 **200**，是真正的登入頁面。

- 原因：此檔在 `dist/` 之外，`build.js` 的清理邏輯不涵蓋它
- 風險等級：**中** — 攻擊者看得到登入頁，可嘗試暴力破解（配合上面「無速率限制」會放大風險）

- 三個處理方向（詳見路線圖）：
  1. 把後台移出 GitHub Pages，改放 Cloudflare Pages + Access（真正的存取控制）
  2. 為 `/api/login` 加上速率限制（擋暴力破解）
  3. 至少把 `admin/public/` 改成不隨 repo 部署

### 測試有效性：用突變測試驗證

新增的兩組功能都做過**突變測試** —— 故意改壞程式碼，確認測試會失敗。
沒有失敗過的測試，不能算是保護。

**發布狀態徽章（5 種突變全部攔截）**

| 突變 | 若未被抓到會發生什麼 |
| --- | --- |
| 「待重建」改判為「已上線」 | 粉飾太平，同事以為已生效 |
| 未上線時仍給可點連結 | 點到 404，就是原本要修的問題 |
| 狀態未知時謊稱「已上線」 | 給出錯誤的安心感 |
| 手動模式謊稱「已上線」 | 同上 |
| 不顯示預計生效時間 | 同事不知道要等多久 |

**登入機構名（6 種突變全部攔截）**

| 突變 | 若未被抓到會發生什麼 |
| --- | --- |
| 失敗時往外拋例外 | **整個登入流程被擋住** |
| 不寫入主標 | 功能等於沒做 |
| 副標不判重 | 出現「XX / XX」重複 |
| 啟動路徑漏接 | 函式寫了但沒人呼叫 |
| 只有英文名時不顯示 | 畫面空白 |
| 改用需驗證的 `/api/config` | 401 → 被自己的攔截器踢出登入頁 |

> 最後一項是真實踩到的坑：一開始用 `GET /api/config`，
> 但**所有 `/api/*` 除了 login 與 health 都需要驗證**，
> 登入前打它會 401，而 401 攔截器會把畫面切回登入頁 ——
> 「想顯示機構名反而把自己踢出去」。已改用免驗證的 `/api/health`。
